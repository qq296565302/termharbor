## 1. S1 — russh 算法兼容性

### 1.1 要回答的问题

需求文档把「`russh` 某些老服务器算法兼容性」列为高危风险，备选方案是换 `ssh2` crate。
但「连不上」有两种可能，处理方式完全不同：

- **A. russh 根本没实现老算法** → 只能换库；
- **B. russh 实现了，只是默认不启用** → 加个配置开关就行。

### 1.2 结果：是 B

矩阵（服务端算法集固定，客户端换档位）：

| 服务端算法集 | 客户端默认档位 | 客户端放宽档位 |
|---|---|---|
| 现代（ed25519 + curve25519 + aes256-gcm + hmac-sha2-256） | ✅ 通过 13ms | ✅ 通过 12ms |
| 全老算法（group14-sha1 + ssh-rsa + aes128-cbc + hmac-sha1） | ❌ `NoCommonAlgo { kind: Kex }` | ✅ 通过 400ms |
| 只给 ssh-rsa 主机密钥（curve25519 + ssh-rsa + aes256-ctr） | ✅ 通过 16ms | ✅ 通过 16ms |

失败时的原始错误恰好把问题钉死了：

```text
NoCommonAlgo {
  kind: Kex,
  ours:   ["diffie-hellman-group14-sha1", "diffie-hellman-group1-sha1"],
  theirs: ["mlkem768x25519-sha256", "curve25519-sha256", ... , "diffie-hellman-group14-sha256",
           "ext-info-c", "kex-strict-c-v00@openssh.com"]   // 没有一个是 SHA-1 的
}
```

### 1.3 从源码核实的算法清单

`russh 0.65` 的 `KEXES` / `CIPHERS` / `MACS` 注册表里**实现了但默认不启用**的：

| 类别 | 已实现 | 是否在默认 `Preferred` 里 |
|---|---|---|
| kex | `diffie-hellman-group14-sha1`、`group1-sha1`、`group-exchange-sha1` | ❌ 默认给了 `SAFE_KEX_ORDER`，只到 SHA-256/512 那几档 |
| cipher | `aes128-cbc`、`aes192-cbc`、`aes256-cbc` | ❌ 默认只有 CTR + GCM + chacha20 |
| mac | `hmac-sha1`、`hmac-sha1-etm@openssh.com` | ❌ 默认只有 SHA-2 系列 |
| host key | `ssh-rsa`（`Algorithm::Rsa { hash: None }`） | ✅ **本就在默认列表最后一位** |

一条容易误判的细节：**`ssh-rsa` 主机密钥默认就能用**，不需要放宽。真正卡住老服务器的是 kex（`group14-sha1`）——因为 OpenSSH 从 7.4 起才把 `curve25519-sha256` 加入默认，更老的设备（CentOS 6 / 嵌入式设备 / 老交换机）只有 DH group1/group14 SHA-1。

### 1.4 结论与产品决策

1. **不需要换 `ssh2` crate。** 风险等级从「高」下调到「中」，且完全可控。
2. M1 要在连接的高级设置里加一个**「兼容老服务器算法」开关**（默认关）：
   - 关：`Preferred::DEFAULT`；
   - 开：默认列表 + 追加 legacy 兜底（现代算法仍排最前，顺序不能反）。
   - `spikes/src/algorithms.rs::client_relaxed()` 就是参考实现，M1 直接搬。
3. **UI 上要提示「连接会比平时慢」**：老算法握手实测 400ms，现代算法 12–16ms，差 25 倍以上。这是算法本身决定的（2048 位 DH 协商），不是 bug。
4. 顺带一条连接检查项：`connection_test` 失败时，如果错误码是 `SSH_ALGO_NEGOTIATION`，直接把「打开兼容模式」作为建议动作弹给用户。

### 1.5 Windows 构建的坑（会阻塞 CI）

`russh` 默认用 `aws-lc-rs`，它在 Windows 上要调 NASM 汇编器：

```text
NASM command not found! Build cannot continue.
```

两条路，建议选第一条：

```toml
# Cargo.toml —— 用官方预编译目标，不需要装 NASM
aws-lc-rs = { version = "1", features = ["prebuilt-nasm"] }
```

第二条是装 NASM 并加进 PATH（`winget install nasm`）。**必须写进 README 的构建前置**，否则新机器第一次 `cargo build` 就卡住，而且报错信息完全看不出缺什么。

## 2. S2 — 终端吞吐与背压

### 2.1 测试设计

- 服务端跑在**子进程**里：否则它的发送缓冲会算进本进程 RSS，读数就没意义了。
- 服务端按 32KB 一块狂推，块里混入中文，保证分包会切在多字节字符中间。
- 客户端链路：`channel.wait()` → 有界队列（64）→ UTF-8 增量解码 → 批量聚合（32KB / 16ms）→ 消费者。
- 两组对比：消费者不限速 vs 每批固定延迟。

### 2.2 结果

| 指标 | 快速消费者 | 慢速消费者（20ms/批） |
|---|---|---|
| 传输量 | 64 MB | 16 MB |
| 耗时 | 0.78s | 15.94s |
| **吞吐** | **82.4 MB/s** | **1.0 MB/s** |
| 分包 / 批次 | 2048 / 2048 | 512 / 512 |
| UTF-8 替换符 | **0** | **0** |
| RSS 基线 → 峰值 | 10.0 → 14.6 MB（+4.6） | 13.5 → 19.1 MB（+5.7） |

IPC 载荷（同一条终端输出批）：

| 载荷形态 | JSON 体积 |
|---|---|
| `{ seq, data: String }` | 32,787 B |
| `{ seq, data: Vec<u8> }` | 114,117 B |
| **膨胀** | **3.5×** |

### 2.3 结论

1. **背压是真的生效。** 吞吐从 82 MB/s 掉到 1 MB/s，等于把消费者速度原样传回了读取端；同时 RSS 只涨了 5.7MB（同期传了 16MB），内存没有随输出增长。这就是有界队列 + 停止调用 `channel.wait()` 的效果。
2. **UTF-8 增量解码器是必需品，不是优化项。** 32KB 块里混着中文、运行 2048 次分包，替换符为 0。作为对照，`spikes/src/utf8_stream.rs` 里有一条测试专门证明朴素做法（`from_utf8_lossy` 逐块解码）在切分点一定会坏。这个解码器 M2 直接搬进 `src-tauri/src/ssh/decoder.rs`。
3. **终端输出必须走 `String`，不能走 `Vec<u8>`。** 实测 3.5 倍差距，和开发计划里的估计一致。这条从「经验判断」变成「有数据」。
4. **82 MB/s 足够。** 真实场景里 `cat` 一个 500MB 日志，约 6 秒传完，期间内存平稳。

### 2.4 两个测量陷阱（写下来免得下次再踩）

- **Windows 的 `sleep` 精度是 ~15.6ms。** 第一版把慢消费者设成「每批 2ms」，测出 2.0 MB/s 并怀疑是 Nagle 问题；实际是 2048 批 × 15.6ms ≈ 32s。**做吞吐测量时，任何小于 20ms 的 sleep 都是无效的**，会让结论跑偏一个数量级。第二版改成 20ms 才拿到可信数据。
- **`nodelay` 在本次测试里没差别**（开启前后都是 82 MB/s）。这符合预期：批量传输本来就不受 Nagle 影响，它影响的是「按键 → 回显」这种小包往返。**交互延迟需要另外测**，见 §4 遗留项。

## 3. S3 — 中文输入法与 WebView

### 3.1 为什么不能自动化

IME 是「操作系统输入法 ↔ WebView 编辑上下文」的交互，没有可编程接口能模拟真实的候选词选择与上屏过程。这一项必须人工在三平台各跑一遍。

### 3.2 取证工具

应用里加了「输入法测试」页（**仅开发构建可见**，`import.meta.env.DEV` 守卫，不进正式包）：

- 左侧是真正的 xterm.js 终端；
- 每次 `onData` 都会把原始字节转成十六进制发给 Rust（`ime_echo` command），再拿回解码结果；
- 右侧逐条列出：字符数、字节数、原始十六进制、Rust 解码文本、是否一致。

**为什么用 hex 而不是直接传字符串**：如果先在 JS 侧转成字符串再传，丢字、替换符这类问题会在传输前就被掩盖。hex 保住了原始字节，出问题时能一眼看出是「少了字节」还是「编码错了」。

### 3.3 手工测试协议

三平台各执行一遍，每项记录「通过 / 异常现象」。

| # | 操作 | 期望 |
|---|---|---|
| 1 | 切中文输入法，输入「你好世界」后回车 | 1–2 条事件，字节数合计 12，`decoded` 完整，无 `�` |
| 2 | 输入「终端港 TermHarbor」中英混排 | 汉字各 3 字节、ASCII 各 1 字节，顺序不乱 |
| 3 | 输入带标点的整句（，。！？「」） | 标点各 3 字节，与汉字一致 |
| 4 | 拼音输入中途按 Esc 取消 | 不发事件，或发可忽略的空事件；不能把拼音字母漏进终端 |
| 5 | 输入后按退格、方向键 | 事件内容是 `1b 5b …` 转义序列，不是字面 `[D` |
| 6 | 用 Shift 切换中英文后连续输入 | 事件边界正确，不丢首字母（IME 切换时首字符丢失是老毛病） |
| 7 | 快速连续输入 20 个汉字 | 事件总数与字节总数对得上，无截断 |

第 4、6 项是历史上最常见的两个 IME bug，重点看。

### 3.4 当前状态

工具已就绪，**尚未在真机执行**——需要人坐在机器前切换输入法。三项里唯一的未完成项。

## 4. 对开发计划的影响

| 风险项 | 原评估 | 更新后 | 依据 |
|---|---|---|---|
| R1 russh 老服务器算法兼容 | 高 | **中（可控）** | 放宽配置实测可连全老算法服务端；不需要换 `ssh2` |
| R2 IPC 终端吞吐 | 高 | **低** | 82 MB/s，RSS 平稳；`String` 比 `Vec<u8>` 省 3.5 倍已量化 |
| R3 WebView 中文 IME | 中 | **待定** | 取证工具已就绪，需三平台人工执行 |

新增两项待办：

1. **构建前置**：Windows 要加 `aws-lc-rs/prebuilt-nasm`，写进 README 与 CI。
2. **M1 增项**：「兼容老服务器算法」开关（约 0.5 人日，含 UI），从隐含需求变成显式任务。

### 仍然遗留的问题

- **xterm.js 真实渲染的高吞吐表现没测。** S2 只覆盖了 Rust 侧链路，`term.write()` 在 80MB/s 输入下会不会掉帧、`scrollback: 5000` 下的内存曲线如何，要到 M2 接上真实终端才能测。这也正是当初把「终端」单独列为里程碑的原因。
- **交互延迟（按键 → 回显）没量化。** 需要在 M2 用真实 SSH 会话测 RTT，并对比 `nodelay` 开关前后的差异。
- **真实老服务器没连过。** 本次用 russh 自建服务端模拟算法集，能证明「算法协商没问题」，但不能证明「某台具体 CentOS 6 上的 OpenSSH 5.3 也没问题」。等有真实机器时，用 `s1_compat` 的思路补一次即可。
